## 0. 一页摘要（新窗口先读这里）

**一句话定位：** **Agent Office 是面向个人与小团队的 AI 原生可视化工作空间**：用户从目标和自己愿意保留的职责出发，系统推荐工作能力与团队，由 Agent 自主组织执行；用户通过熟悉的办公空间理解工作，在必要时作出关键决策，并检视可追溯的成果。

**首个切入点：** 数字成果交付，例如品牌 VI、展示网站、产品原型与 AI 原生软件开发。**不是**首发即支持所有行业的通用企业自动化平台。

**通用底层：** Goal / Capability & Organization / Execution / Control / Evidence & Outcome。**用户心智：Goal（工作目标）→ Team（工作团队）→ Practice（被验证可复用的工作方法）。**

**默认体验：** “目标模式”优先：用户说清目标，AI 推荐组织方案；“组织模式”保留给希望自定义部门、职责、工具和政策的进阶用户。用户不必先创建公司、扮演 CEO 或理解 Agent 编排技术。

**角色结构：** 稳定的“部门/能力单元”可绑定执行器（例如 Codex 等）；部门负责人是组织与协作入口，动态子 Agent 是按任务产生的执行实例。**部门、岗位、执行器、子 Agent、3D 人物不是同一概念。**

**M1 目标：** 做一个 **完全由 Mock 事件驱动的、能回放的多 Agent 工作世界**。演示“创建品牌 VI 并开发展示网站”：两个部门负责人，按需出现研究、视觉设计、前端开发、测试等子 Agent；负责人按约定路线行走和交接，子 Agent 主要在固定工位展示工作；包含一次人类关键决定和成果交付。不接真实 Agent、不制作复杂微表情、不做完整编排编辑器或人效预测。

**M2 重点：** 用户通过目标输入与可视化方式调整团队/职责/授权并模拟执行；任务完成后可选择保存经过相应验收的 Team + Practice。**M3** 再接首个真实 Agent SDK；**M4** 才探索组织/流程模拟与对比分析。

**关键价值判断：** 可视化负责 *看懂、发现异常、方便干预*；效率来自背后的 Agent 编排、工具执行、验证、政策与交付控制。可视化是否提高普通人的编排能力与判断质量，仍须通过实际用户测试验证。

## 1. 背景、问题与产品目标

### 1.1 用户问题

普通人往往知道想达成什么结果，却不知道如何挑选 Agent、设计多 Agent 分工、配置工具、追踪执行、判断质量和何时介入。传统技术工作流的概念（SDK、Skill、MCP、执行日志、子线程等）不应该成为普通用户完成目标的前置知识。

我们希望以用户熟悉的**办公室、部门、岗位、任务交接、讨论、成果台**作为交互隐喻，将复杂的执行体系转化为可理解、可观察、可控制的工作空间。

### 1.2 希望实现的用户结果

1. **提出目标而不是学习技术。** 可以自然语言描述想做的事情，系统主动提出可理解的能力分工与工作建议。
2. **选择自己参与的位置。** 用户只保留熟悉、擅长或愿意承担的职责；其他工作可在授权范围内交给 AI。
3. **低成本理解进展。** 看懂谁负责什么、有哪些动态执行实例、工作交接在哪、哪些任务受阻与何时需要人决策。
4. **有限而有效的人工参与。** 人负责目标、重大边界与决策，不被低价值的过程确认打断。
5. **对结果保持掌控。** 交付物与证据可查看、可验证，不能只靠 Agent 声称完成。
6. **累积可复用的方法。** 经过真实检验的团队配置、交付规范和执行策略，可以保存为 Practice，形成用户自己的 AI 工作组织。

### 1.3 不是要做什么

- 不是一款必须玩经营游戏才能工作的产品。
- 不是以复杂 3D 动画、自由漫游、真人呼吸/口型为核心卖点。
- 不是一个要求用户手动画完整 BPMN 流程的传统自动化产品。
- 不是再开发一套与 Codex/Claude 等竞争的通用 Execution Agent。
- 不是默认认为“越多子 Agent 越高效”。
- 不是把 AI 的 Claim 当作 Evidence，或把模拟时序当真实人效结论。

## 2. 产品定位与阶段性市场选择

### 2.1 产品工作定位（当前方向）

**Agent Office：面向个人与小团队的 AI 原生工作空间。**

优先帮助非专业 Agent 编排者，以自然语言目标与熟悉的组织隐喻来组织 AI 完成**数字成果交付**。

### 2.2 为什么先聚焦数字成果交付

- 目标和交付物更容易定义：品牌资产、设计稿、网站、代码、测试报告、原型等。
- 多种角色协作关系清楚：研究、策划、设计、研发、验证。
- 更容易得到可检查的结果证据，而不只是“看起来有进展”。
- 与当前已积累的 AI 原生开发和交付治理知识高度吻合，减少首期跨行业集成风险。

**首批使用者假设：** 数字产品创业者、独立构建者、设计师、产品经理、自由职业者、小型团队，也包括通过 AI 构建网站或应用的非程序员。此为待验证目标用户选择，非已证明的市场结论。

### 2.3 三个未来方向的关系

| 方向 | 共同底层 | 当前取舍 |
| --- | --- | --- |
| 个人可复用工作流 | Goal、Team、Practice、执行与结果 | 从数字成果场景逐步扩大 |
| AI 原生开发交付 | 同一底层，具备成熟代码验证及交付控制机制 | **首期关键验证环境** |
| 企业 AI 组织转型/模拟 | 同一底层，额外需要组织权限、历史样本、成本与业务事实 | **后期研究方向**，不进入 M1 |

底层应具备扩展性，但第一版不打造通用行业软件的庞大 UI、权限和数据集成体系。

## 3. 与源点AI、阿造现有冻结架构的边界

### 3.1 继承但不重定义的事实

此项目需要尊重既有上位文档：

- 《源点AI 产品家族架构与三端责任边界冻结 V1.0》：人类/组织 Authority；External Agent 负责 Execution；Claim、Evidence、Outcome 分离；控制状态不覆盖 Source of Record；阿造长期承担 Product Delivery Assurance。
- 《源点AI 品牌架构与产品家族手册 V4.0》：当前阿造正式类别为“AI产品交付掌控系统”，核心语义“掌控”，不与 Coding Agent 竞争；品牌 Y 形母图形与现有识别色仍适用。
- 《AI 原生软件开发工作流与 Codex 工程治理规范 V2.0》：Intent → Execution → Evidence → Outcome；已批准目标、执行计划、真实证据与结果不可互相替代，日常流程应尽量减少不必要的人类操作。

### 3.2 当前产品边界判断

**本工作空间先作为阿造相关能力的 UX / 产品实验，不能因为新视觉形态就静默将阿造的冻结品类改为“通用 AI 企业操作系统”。**

若后续验证显示一般工作组织、企业模拟已经构成实质新增产品责任，则由产品负责人发起适当的架构与品牌 Revision；在此之前，将“通用 AI 工作空间”理解为长期能力探索，不是已经生效的新品牌事实。

### 3.3 品牌视觉衔接

A1.1 的暖白、木色、青绿色、弧形微缩办公室继续作为当前演示的视觉基准。正式阿造品牌体系（如 Y 形 DNA、Coach Indigo `#5968F2`）在产品化时需要设计衔接；不能把 A1.1 临时环境色未经决策直接变成新的母品牌识别色。

## 4. 统一的领域模型

### 4.1 五层系统责任

1. **Goal / Intent：** 目标、结果定义、约束、用户角色、接受标准。
2. **Capability & Organization：** 部门/能力单元、职责、负责人、可用执行平台与协作建议。
3. **Dynamic Execution：** 任务、步骤、真实或模拟执行实例、子 Agent、工具调用、交接。
4. **Control & Decisions：** 自主权限、风险、人工介入、审批、暂停/恢复、异常处理。
5. **Evidence & Outcome：** 交付物、证明、验收、质量、成本与可复用方法。

这五层是产品责任/领域划分，**不要求对应五个模型或五种独立后端服务**。

### 4.2 用户心智：Goal / Team / Practice

| 概念 | 用户理解 | 系统内涵 |
| --- | --- | --- |
| **Goal** | 我要完成什么 | 意图、范围、成功条件、授权边界 |
| **Team** | 谁能帮我完成 | 能力分工、负责人、执行器、动态工作实例 |
| **Practice** | 哪种工作方法已被证明可复用 | 团队配置、交付标准、权限、上下文、协作与验证策略的可版本化组合 |

**Practice 只有在符合明确验收条件后才标记为已验证。** Mock 演示最多显示“模拟演示完成，可保存配置草稿”，不得声称真实工作流效率或质量已得到验证。

### 4.3 关键对象不可混淆

- **Department / Capability Unit：** 稳定的领域职责，例如“品牌设计部”。是逻辑能力容器，未必等于实体部门。
- **Role / Position：** 职责模板，例如研究员、品牌设计师、前端开发。
- **Agent Provider / Executor：** 实际执行入口（Codex、Claude 等），不同 SDK 可观测能力不同；某个产品是否支持的事件需逐一验证。
- **Lead Agent：** 一个团队/部门的负责者或调度入口；可绑定执行器，不必额外部署一套新的 Manager 大模型。
- **Worker / Sub-agent Instance：** 一次执行中的临时子任务主体；可能被真正观测到，也可能在 Mock 中模拟。
- **Avatar / Desk：** UI 的可视化对象，不自动代表独立运行实例或真实“人”。
- **Decision / Artifact / Evidence：** 决定、交付物与可验证证据分别建模。

**建议：一个执行平台可服务多个能力单元，多个任务可复用同一部门配置；不能强制“一个部门必须对应一个物理模型/独占 Agent”。**

### 4.4 用户角色与授权分离

用户可以说“我只负责品牌创意方向/最终决策”，但预算、对外发布、数据权限及其他重大 Authority 不因角色描述而自动转让给 AI。默认策略：低风险日常执行可自动；重大改变目标、扩大授权、对外不可逆操作等依政策请求授权。

## 5. 核心交互模式

### 5.1 双入口

**A. 目标模式（默认）：**

`自然语言目标 → AI 推荐能力/团队与计划 → 用户确认必要边界 → 自主执行 → 例外与决策 → 交付证据 → 可选择保存实践`

用户无须先搭建公司和部门。

**B. 组织模式（可选）：**

用户主动创建或调整部门、绑定执行器、定义角色与权限，以及工作方法。适用于希望长期经营自己工作体系的进阶用户。

两种入口消费同一套 Goal、Team、Execution、Control、Outcome 数据，不创建两套互相漂移的真相。

### 5.2 从一次目标逐渐形成 AI 工作组织

示范过程：

1. 用户说：“制作一个品牌网站。”
2. 系统推荐“品牌设计”和“网站研发”能力；用户可编辑，但不必管理每个子任务。
3. 执行时临时出现研究、设计、前端和测试子 Agent，是否真正创建多个子 Agent 由执行系统与实际需要决定。
4. 过程中如果需要确认品牌方向，向用户请求重大决策。
5. 完成后展示成果和适用证据；若通过对应的真实验收，系统可以提议保存成“品牌网站工作团队/工作方法”。
6. 下次类似任务复用配置，并依据新目标与约束调整。

用户的工作组织是经任务逐渐沉淀的“资产”，不是第一次使用时的配置负担。

### 5.3 工作空间的三种功能区域

- **部门工作区：** 可命名能力区与负责人工位。
- **动态执行席位：** 按任务出现的子 Agent；在 M1 中原则上固定工位，展示真实/Mock 工作状态。
- **共享协作设施：** 讨论区、会议点、跨部门交接点、成果台和人类决策入口。

视觉空间表达组织语义，但不会成为底层权限或事实的唯一来源。重要详情、配置、结果使用清晰的 2D 面板展示；3D 用于总览、空间关系和吸引力。

### 5.4 角色动作策略

**M1 固定原则：** 负责人 Agent 可以按预设路径行走、转身、交接、到会议区；子 Agent 主要在固定工位，通过出现/消失、岗位道具、任务卡和少量动作表达执行。允许之后放宽，但此阶段不开发全体人物的复杂移动系统。

**不做：** 精细呼吸、复杂微表情、口型同步、大量随机闲逛、真实物理碰撞、开放世界路径规划。**做：** 基础 Idle、Walk、Work、Discuss/Present（可重用短动作）、可读状态与清晰的动作过渡。

## 6. M1｜Living Office Demo：当前首要里程碑

### 6.1 目标陈述

**以 Mock 数据完成“目标 → 推荐团队 → 动态子 Agent 执行 → 交接/讨论 → 人类关键决策 → 成果展示”的可视化闭环。**

M1 验证的是“工作世界能否让普通人直观理解多 Agent 协作”，不是验证真实 Agent 的推理能力、人效提升或跨平台 SDK 集成。

### 6.2 建议的唯一演示故事

**业务目标：** “为一个新品牌制作品牌 VI，并开发一个品牌展示网站。”

**人类用户：** “品牌主理人”，只保留创意方向、必要的预算/发布授权和最终结果判断。**没有必须扮演 CEO 的操作。**

**组织：**

- 品牌设计部：1 位负责人；按任务需要出现“品牌研究”“视觉设计”子 Agent。
- 网站研发部：1 位负责人；按任务需要出现“前端开发”“测试/检查”子 Agent。
- 共享区域：讨论/会议、跨部门交接与成果交付。

首版最少两个负责人、若干动态工位。为了证明“动态增减”，演示可以出现 4 个子 Agent，但不要求四个在所有镜头同时显示；可以折叠工作组。**人数是演示配置，不是系统硬编码最大值。**

### 6.3 建议演示时间线（事件驱动，非固定秒数）

| 场景 | 用户看到 | 说明 |
| --- | --- | --- |
| S1 目标建立 | 用户提交“VI + 网站”目标 | Mock；项目状态明确标记“模拟演示” |
| S2 组织推荐 | 两个部门高亮，负责人获得工作 | 推荐内容由 Mock 脚本提供，不声称已由真实 AI 推理 |
| S3 动态员工 | 研究/设计/前端/测试按需出现、就位并执行 | 员工可固定席位；显式体现领导与临时实例区别 |
| S4 协作交接 | 负责人沿预设路线到讨论区，交接设计成果给研发 | 交接卡片绑定具体模拟 Artifact/Task ID |
| S5 请求决策 | 用户收到“确认品牌方向”的模拟审批请求 | 暂停相关依赖；可演示批准与退回两种结果 |
| S6 继续执行 | 决策后后续任务推进，检查子 Agent 完成验证 | 可回放，不能靠动画直接改变业务状态 |
| S7 交付成果 | 成果台展示 VI、网站缩略图、模拟测试信息 | 明确“模拟成果”；详情面板可阅读 |
| S8 复用提示 | “保存这套工作团队与方法？” | M1 可仅作为概念提示/草稿；实际保存与复用进入 M2 |

### 6.4 最小系统组成

1. **MockScenarioRunner：** 脚本事件源；可播放、暂停、复位、倍速和确定性回放。
2. **Goal/Team/Work 数据模型：** 不把人物对象当任务实体。
3. **Behavior Director：** 把事件翻译成移动、站位、状态和动作意图。
4. **Navigation Anchors / Waypoints：** 固定工位、走廊、交接点、会议点；首版不做动态 NavMesh。
5. **Avatar & Motion Controller：** 用少量预制动作、位置和朝向插值，按角色分离状态。
6. **2.5D + 2D UI：** 正交办公室总览，点击人物可看到身份/角色/模拟任务；点击成果可看具体说明。
7. **Decision Gate：** 模拟暂停和恢复，可供用户真实点击，产生 Mock 决策事件。
8. **Artifact Viewer：** 对交付物类型、来源、模拟性和验证范围进行明确标注。

### 6.5 Mock 事件建议（内部草案）

`goal.created`、`organization.recommended`、`department.activated`、`worker.spawned`、`task.assigned`、`task.started`、`task.handoff`、`collaboration.started`、`meeting.started`、`decision.requested`、`decision.resolved`、`artifact.delivered`、`practice.suggested`。

每个事件最少携带：`eventId`、`scenarioId/runId`、`sequence`、`occurredAt`、`type`、相应 `goalId / taskId / agentId / departmentId` 关联与 `source: "mock"`。具体字段由后续 schema 设计拥有，本文不固定最终 API 契约。

**关键规定：** 业务事件先更新工作状态，视觉层只是投影和表现；不能依靠动画播放完毕来伪造任务已完成。

### 6.6 M1 验收清单

**功能验收（工程自验记录；不代替主创体验验收）：**

M1 核心交互已完成本地验证，证据见 交付报告（本地归档 / 外部参考，未随版：`docs/production/M1_DELIVERY_REPORT.md`）。目标 GPU 性能和下述用户理解假设仍未验收。

- [x] 一个可运行的 2.5D 办公空间，包括设计、研发和共享区。
- [x] 用户提交或触发一个 Mock 目标；系统展示推荐的团队结构。
- [x] 至少两位负责人和多名按任务出现的子 Agent；状态相互独立。
- [x] 负责人按确定路线行走、转身、到达讨论/交接位置，人物不严重穿过家具。
- [x] 子 Agent 在固定工位展示工作，能出现/结束并关联到模拟任务。
- [x] 一次明确的部门间交接与一次简短讨论/会议演出。
- [x] 一次可由用户操作的关键决策，决策结果影响后续 Mock 执行。
- [x] 可查看任务与成果的 2D 详情，且全部模拟内容有清楚标记。
- [x] 场景播放/暂停/重播有效，相同事件输入可得到一致业务状态。
- [x] 资产、模型、动效与事件数据分离，方便后续切换到真实 Provider Adapter。
- [ ] 浏览器实际加载并通过受影响的功能/视觉/性能检查。


**用户理解验证（非自动完成）：** 邀请没有多 Agent 技术背景的人观察，确认能否识别部门、负责人/员工、交接、待决策点和交付结果。后续再对照 2D 任务界面测试准确率、时间及主观负担。**不得以漂亮截图或观看时长单独证明效率提升。**

### 6.7 M1 明确不做

真实 Codex/Claude/Qoder/WorkBuddy SDK 集成；真实团队自主优化；完整员工/部门编辑器；实际保存并复用 Practice 的后端；精细脸部动画；复杂多人避让；完整企业权限与审批；企业人效预测；多组织对比和真实执行成本报告。

### 6.8 开发顺序建议

先建立最薄的“目标 → 推荐团队 → 执行事件 → 负责人移动/子 Agent 就位 → 人决策 → 成果”可运行切片，再逐步提升人物动画、材质和空间细节。**不等待所有人物达到电影级精细动作才开始业务场景演示。**

现有 Tripo 人物高模仍是造型来源；低模、绑定与动作生产按照已审核的 G2.5/G2.6 工作流推进。可在初期使用占位角色验证事件与路径，随后替换成正式资产。视觉冻结 A1.1 不代表模型已经具备动画生产质量。

## 9. 决策记录与开放问题

### 9.1 当前已达成的产品方向共识（非永久冻结）

- **D01：** Agent Office 面向个人与小团队，首个切入点为数字成果交付。
- **D02：** 底层按 Goal / Capability & Organization / Execution / Control / Evidence & Outcome 分层。
- **D03：** 用户工作心智为 Goal / Team / Practice。
- **D04：** 保留目标模式与组织模式，默认目标优先。
- **D05：** 用户只需保留熟悉或愿意负责的职责，其他交给获授权的 AI；角色和权限分离。
- **D06：** 部门是相对稳定的能力容器，子 Agent 是动态任务执行实例。
- **D07：** Agent-first：AI 在授权边界内自主规划/执行；人负责重大决策、异常和结果把关。
- **D08：** M1 是 Mock 驱动的多 Agent 工作世界，先验证可理解的动态协作，不接真实执行器。
- **D09：** M1 只有负责人优先参与走动/会议；子 Agent 主要固定工位，后续可演进。
- **D10：** 不把 3D 可视化当效率证明；采用 3D 总览 + 2D 精确配置/成果详情。
- **D11：** A1.1 暖色视觉方向及原 3D 母版继续保留。2026-11-06 B1.0 任务明确授权独立 PNG + React / DOM / SVG 展示路线，不在该展示层加载 3D 引擎；此变更不重开原资产母版或 M2 / SDK 范围。
- **D12：** M2 先做编排与可复用工作方法，M3 再接真实 Agent，M4 再做流程模拟对比。
