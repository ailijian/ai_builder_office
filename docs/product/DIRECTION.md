# Agent Office 产品方向

> Status: ACTIVE · 2026-11-07 · Working Draft V0.1，整理既有共识；不新增产品实施授权

## 定位与用户价值

Agent Office 是面向个人与小团队的 AI 原生可视化工作空间。用户从目标和愿意保留的职责出发，由系统推荐能力分工与团队；通过熟悉的办公空间理解工作，在需要时作出关键决策，并检视可追溯的成果。

首期聚焦品牌 VI、展示网站、产品原型和 AI 原生软件开发等数字成果交付。目标和交付物较易定义，研究、设计、研发、验证的协作关系清楚。首批用户假设包括独立构建者、设计师、产品经理、自由职业者、小团队及通过 AI 开发产品的非程序员；这些是待验证选择。

希望用户可以：

1. 用自然语言提出目标，无须先掌握 SDK、MCP、Skill 或 Agent 编排。
2. 只保留熟悉、愿意参与或必须负责的职责，在授权范围内让 AI 执行其余工作。
3. 看懂谁负责什么、任务在哪里交接、何时受阻以及何时需要人决策。
4. 阅读交付物和验证证据，掌控结果，而不是仅相信“已完成”的陈述。
5. 将经过实际验收的团队配置与工作策略沉淀为可复用方法。

可视化服务于理解、异常发现和人工干预。效率来自执行、验证和交付控制；漂亮场景、模拟时长或子 Agent 数量都不能单独证明效率提升。产品不要求用户扮演 CEO、经营虚拟公司、自由漫游或先画完整流程图，也不另造与外部执行 Agent 竞争的通用执行器。

## 用户心智与领域责任

核心体验为 **Goal → Team → Execution → Decision → Outcome → Practice**。

| 用户概念 | 含义 |
| --- | --- |
| Goal | 我要完成什么：意图、范围、成功条件与授权边界 |
| Team | 谁能帮我完成：能力分工、负责人、执行器和临时工作实例 |
| Practice | 哪种方法值得复用：团队配置、交付标准、权限、上下文、协作与验证策略 |

Practice 只有满足明确验收条件才能标记“已验证”。当前 Demo 导出的是未验证配置草稿，不能据此声称真实工作方法有效。

底层按五层责任理解，不要求对应五个服务：

| 层 | 责任 |
| --- | --- |
| Goal / Intent | 目标、结果定义、约束、用户角色、接受标准 |
| Capability & Organization | 部门、职责、负责人、可用执行平台和协作建议 |
| Dynamic Execution | 任务、步骤、执行实例、工具调用与交接 |
| Control & Decisions | 自主权限、人工介入、审批、暂停 / 恢复和异常 |
| Evidence & Outcome | 交付物、证明、验收、质量、成本和复用 |

这些对象必须区分：

- **Department / Capability Unit** 是相对稳定的能力容器，不必对应实体部门。
- **Role / Position** 是职责模板；**Provider / Executor** 是实际执行入口。
- **Lead Agent** 是组织与协作入口，不意味着另建一个 Manager 大模型。
- **Worker / Sub-agent Instance** 是某次任务中的临时执行主体；当前 Demo 仅模拟其生命周期。
- **Avatar / Desk** 是视觉对象，不等于独立 Agent 会话或真实执行实例。
- **Decision / Artifact / Evidence** 分别表示决定、交付物和可验证证据。

一个执行平台可服务多个能力单元，部门配置可跨任务复用。角色选择与 Authority 分离：用户说“我只负责创意”不会自动转让预算、发布或数据权限。

## 交互原则

**目标模式优先。** 自然语言目标 → 推荐团队和计划 → 确定必要边界 → 执行 → 例外与决策 → 交付证据 → 选择保存实践。首次使用不要求先搭建部门。

**组织模式供进阶使用。** 用户可调整部门、执行器、职责、权限与工作方法。两种入口消费同一组 Goal、Team、Execution、Control、Outcome 数据，不建立平行状态源。

工作空间包含部门工作区、动态执行席位和共享协作设施。部门负责人组织、交接和讨论；临时子 Agent 按任务出现并在完成后释放。人物数量和职责分配是场景配置，不是系统人数上限。

空间承担总览和组织关系表达；精确配置、长文本、审批、证据和成果使用可访问的 HTML 界面。保留温暖、精致的微缩办公室方向与克制动效。动画只表达事件，不推断完成或批准；未知、离线、推断和纯演示应有明确区分。

## 当前验证故事

“为一个新品牌制作品牌 VI，并开发一个品牌展示网站。”

目标建立 → 推荐能力团队 → 负责人组织 → 子 Agent 按任务执行 → 跨部门交接 / 讨论 → 人类确认品牌方向 → 批准后继续或退回后阻断 → 成果交付 → 提示保存 Team / Practice 草稿。

M1 最初使用两负责人、四执行角色；B1 已按后续用户要求调整为三负责人、三执行角色与女性接待。本文只维护故事目的，实际角色 ID、时间点、事件及审批分支以 [Mock 契约](../web/MOCK_SCENARIO.md) 为准；截图与功能检查以 [验收记录](../web/ACCEPTANCE.md) 为准。

当前验证的是普通人能否理解多 Agent 协作，不是验证真实 Agent 推理能力或人效提升。M2–M4 顺序及未决事项统一维护在 [路线](ROADMAP.md)。

继续保留原讨论的约束：人类 / 组织持有 Authority，External Agent 负责 Execution；Claim、Evidence、Outcome 分开；控制状态不覆盖 Source of Record。Agent Office 作为阿造相关 UX / 产品实验，不因视觉变化静默修改“AI 产品交付掌控系统”的产品责任或正式品牌品类。

正式产品化涉及责任或品牌修订时，应回查原文件及适用的批准流程。原讨论中的 Y 形视觉 DNA、Coach Indigo `#5968F2` 与 A1.1 暖白 / 木色 / 青绿的衔接仍待相应设计决定；环境色不自动成为新的母品牌识别色。
